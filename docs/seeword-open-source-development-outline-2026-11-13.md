# SeeWord 开源学习项目开发方案大纲 v0.2

日期：2026-11-13。状态：**v0.2 已接受为 P0 的讨论与工作基线，仅此而已；P0 尚未通过，P1–P5 未放行。** 本次只拆分文档和启动 P0 事实盘点，评审范围、阻塞与检查日期见 [P0 工作记录](open-learning/p0-worklog.md)。

本文整理项目方向、架构建议、阶段依赖和验收设计，不表示立即开始业务代码改造、迁移或部署。“全部开源”是已确认方向，具体许可证尚未确定，仓库根许可尚未修改。**同意修订本大纲，不等于批准其中待确认的产品、许可、数值或接口决策。**

v0.2 修订重点：前置 P0 阻塞决策；明确内容访问与分发边界；补齐回退和引用规则、阶段依赖、账号生命周期、测试设计、风险与决策责任。沿用原文件路径，避免产生两份并行维护的大纲。

## 一、项目定位与核心目标

### 1.1 项目定位

**SeeWord 是围绕真实语境组织学习资料、提供学习能力的全开源项目。**

以视频和双语字幕为当前切入点，让学习者完成：

> 找到材料 → 理解词句 → 回到原句 → 练习与复习 → 持续学习。

SeeWord 网站是官方客户端；第三方应用和 Agent 可以通过开放格式与接口复用同一套能力，而不必依赖官方界面或官方模型。

本文术语：

- **SLCS**：项目已有的视频学习包规范及独立读取工具，用 JSON 描述来源、双语字幕、词汇和定位信息；正式字段与版本规则以规范文档为准。
- **Astryx**：Meta 的开源设计系统，基于 React 19+ 和 StyleX；已按[接入记录](evidence/astryx-integration/acceptance.md)在词汇页试点。来源核对与固定提交见 [P0 工作记录](open-learning/p0-worklog.md)。本方案只把它作为基础控件候选，不代表全站已迁移或已完成人工验收。
- **MCP（Model Context Protocol）**：Agent 宿主接入工具和上下文的协议；协议适配不代替服务端鉴权和业务规则。
- **语境出现项**：某个词或表达在某份材料具体修订中的一次出现，不等同于词形、词义或个人掌握状态。

### 1.2 三个长期目标

1. **提升学习体验**：资料有广度，也有可逐层深入的语境、解释、练习和复习能力。
2. **降低建设与维护成本**：贡献者容易参与，维护者能够清楚审核、修订、发布和回退。
3. **方便独立使用与第三方接入**：学习包可以独立消费；网站可以自托管；Agent 可以按权限读取资料和衔接学习状态。

### 1.3 项目优势的积累方向

不依赖隐藏代码，而是积累：

- 可追溯、可定位、可持续纠错的学习资料。
- 同一表达在不同材料中的真实用法。
- 连贯、可靠的学习流程。
- 清楚稳定的开放契约与贡献机制。

## 二、确认状态与范围边界

### 2.1 已确认方向

- 项目自有前后端、工具和协议实现以**全部开源**为方向。
- 采用渐进重构，不整体推倒重写。
- 优先复用现有 SLCS、发布修订、学习记录与播放器能力。
- 网站与第三方入口共用业务规则，不维护两套学习系统。
- 以学习价值、可维护性和可复用性判断重构成果。

### 2.2 当前建议，尚未定稿

- 保留 FastAPI、Next.js 等现有技术栈。
- 使用小型参考语料集验证产品与接口。
- Astryx 作为用户端基础控件的渐进统一方案。
- 先完善第三方只读能力，再开放受控写入。

**第三至九章的新增流程、架构、接口范围和试验安排均为方案建议；其中引用的既有契约与项目不变量继续有效。** 第十章记录决策状态和最晚确定阶段；没有指定人员或批准数值的事项，不视为已经落实。

### 2.3 不纳入首批范围

- 微服务拆分、通用 Agent 框架、复杂插件市场。
- 联邦同步、跨平台自动同步、完整多租户系统。
- 一次性支持所有材料类型与所有 Agent 宿主。
- 未经评估切换复习算法。
- 恢复已下线的收费、会员和退役功能。
- 生产部署、业务库迁移或破坏性清理。

**源码开源不等于第三方媒体和用户数据可以公开；也不自动取消现有站点登录边界。** 全站源码开放仍须落实许可与发布审查，目前不能宣称根许可已完成开源转换。

## 三、产品与学习资料体系

### 3.1 以真实语境为基本组织单位

区分以下对象，避免混成一份“大内容”：

| 对象         | 职责                             |
| ------------ | -------------------------------- |
| 材料身份     | 标识一份材料及其来源             |
| 材料修订     | 固定某一次具体内容               |
| 语境出现项   | 固定某个词或表达在原句中的位置   |
| 共享学习内容 | 语境释义、搭配、比较、练习       |
| 个人学习事实 | 收藏、作答、提示使用、复习记录   |
| 个性化辅导   | 针对当前用户问题生成的解释与建议 |

### 3.2 内容分层与质量标注

- **基础层**：原文、译文、时间、锚点、来源。
- **增强层**：语境释义、表达比较、相关用法、经过核对的练习。
- **个性化层**：按需模型辅导，不自动写回公共资料。

保持 SLCS 基础契约轻量。新增内容不得通过任意加字段或放宽校验塞入 v0.1；需要跨客户端交换时，再设计版本或配套工件。

增强内容进入共享资料前，建议在候选／审核记录中保存：

- 原始依据和生成、编辑方式；模型辅助时记录必要的提供方、模型标识与生成时间，不保存凭据。
- 未核对、已核对或存在争议的状态，以及核对人、时间和受影响范围。
- 采用的内容许可、署名及提供方条款核对结论；模型输出不默认可按任意许可证再分发。
- 错误反馈入口、替代修订和停用范围。严重错误先停止受影响练习或用途，不等待整包重新编排。

这些是拟补充的审核要求，不表示现有包已有相应字段。对外展示方式和交换格式另行确认，不把未核对生成内容标为可靠答案。

### 3.3 广度与深度建设

**广度**关注主题、难度、表达场景和学习目标的覆盖，而不只是资料数量。

**深度**关注语境准确、用法比较、主动回忆或应用，以及原始依据的可回查性。

首期通过少量人工编排的主题路径验证，不以前置建设复杂推荐系统为条件。参考语料的主题与难度取决于 P0 的目标学习者，不能先大量采集、再反推学习目标。

### 3.4 贡献、反馈与发布流程

```text
候选材料／局部纠错／使用反馈
        ↓
最小必要证据整理、隐私与授权核对
        ↓
可审阅的候选修改与差异
        ↓
自动检查 + 按影响范围人工审核
        ↓
符合契约的候选学习包或配套内容
        ↓
显式发布新修订
        ↓
继续使用与反馈；必要时撤回或回退当前版
```

普通贡献者可以只报告或修正一处问题，不必完成整套生产流程。私人对话、个人作答和学习记录不得因“使用反馈”自动变成公共资料；需要引用时，先取得适当授权并进行隐私处理。

正式发布遵守既有质量门，不通过放宽检查增加数量。候选生成、审核和正式发布分开；模型不能自行发布。

### 3.5 修订、回退与稳定引用

本节将既有 SLCS 修订和撤回规则转成 P1 验收要求，不另立一套契约。具体规则认第十章链接的 SLCS 规范与社区治理文档。

| 操作           | 含义                                                 | 对历史引用与学习事实的影响                                       |
| -------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| 内容纠正       | 生成新修订，记录差异并复核受影响用途                 | 不覆盖旧修订正文，不改写历史学习事实                             |
| 回退当前版     | 复核后显式将获准的旧修订发布为当前版，遵守既有发布门 | 仅改变“当前版”入口；固定到其他修订的引用不跟随切换               |
| 撤回修订       | 停止在线提供该修订获准范围内的内容                   | 保留引用与个人学习事实；受影响入口显示不可用，不自动换成其他原句 |
| 恢复已撤回修订 | 重新核对内容、用途和现行发布条件后显式恢复           | 不是绕过撤回的自动回退或普通读取重试                             |

跨客户端引用必须固定材料、具体修订及段／词锚点；本地包使用规范的指纹版本与指纹识别内容版本，在线修订标识如何映射到包身份须在 P1 明确。仅持有材料 ID 的“当前版查询”与固定引用解析是两种不同操作。

无法解析或存在歧义时明确失败，不静默跨修订重定位。历史修订可读与否仍取决于当前可见性和用途许可。在线撤回不承诺收回公开 Git 历史、已下载包或第三方副本。

## 四、目标技术架构

**状态：以下为保留现有技术栈、渐进补缺的建议，不是新的框架冻结或目录迁移决定。**

### 4.1 总体结构

**模块化单体 + 独立读取器 + 按需启用的生产与模型能力。**

```text
SeeWord 网站                 第三方应用／Agent
      │                             │
      └──── 在线 API／协议适配 ──────┘
                       │
                共享学习应用服务
                       │
          业务数据库与材料修订
                       │
              可重建的检索索引

SLCS 学习包 → 独立读取器 → CLI／本地 MCP
```

### 4.2 技术栈建议与检索验证

| 部分     | 建议                                                    |
| -------- | ------------------------------------------------------- |
| 后端     | 继续使用 FastAPI、SQLAlchemy async、PostgreSQL、Alembic |
| 异步任务 | 保留 Celery 和现有队列边界                              |
| GPU      | 保持独立组件，仅作者侧生产任务按需使用                  |
| 前端     | 继续使用 Next.js、React、Tailwind、Zustand              |
| 基础控件 | Astryx 渐进接入，不立即替换全部共享组件                 |
| 检索     | 先实测现有数据库与可重建索引，不预置向量数据库          |
| 模型     | 可替换、可选，不成为阅读与确定性练习的前提              |

不先追逐新版本或新框架；依赖升级由兼容、安全和实际收益驱动。

P0 建立检索测试卡，P1 随真实参考语料补齐查询与预期结果，P3 对候选实现实测。测试卡须提前固定：

- 材料、字幕段、语境出现项的数量，以及目标扩展规模；真实语料与合成压力数据分开记录。
- 精确表达、约定的词形变体、短语、同形异义、无结果和权限过滤等查询；未支持的检索语义明确排除。
- 人工核对的相关结果集、关键必达结果，以及适用时的前 k 项命中／召回目标，不能只凭“搜得到”判断。
- 运行硬件、数据库与索引版本、并发、冷／热状态、计时边界、样本数、p50／p95 延迟及事先确定的目标。
- 分页无重复漏项、固定引用正确、受限片段不泄露，以及索引重建后的结果一致性。

数值目标由试验资源与任务确定并留痕，本稿不宣称已达到任何规模或延迟。只有实测不足、且排除查询和索引设计问题后，才评估新增检索基础设施。

### 4.3 后端职责边界与生命周期

- **材料与发布**：导入、校验、修订、用途、发布、撤回。
- **读取与检索**：跨材料查询、语境定位、引用解析。
- **学习状态**：收词、练习、复习、恢复与历史。
- **辅导运行**：对话、上下文、模型调用、取消和恢复。
- **接入适配**：HTTP、CLI、MCP，共用应用服务。
- **账号生命周期**：本人访问、导出、注销删除；第三方委托授权、轮换和撤权。

先统一用例和事务边界，再决定是否搬目录；不提前建立大量空领域包。

**P2 只要新增个人学习数据，就要同时覆盖本人权限、导出与注销删除，不能等到 P4。** 先核对已有路径再补缺，不重建同义系统。P4 增量处理第三方连接和委托访问；撤销连接停止后续访问，不等同于删除本人学习历史。所有新增记录都应明确保存期限、清理关系和必要审计边界。

### 4.4 必须保持的不变量

- 错误 envelope、鉴权链和服务端判分保持一致。
- 重试不能重复产生学习事实。
- 材料修订与引用不静默漂移，完成记录不自动代表新版内容已掌握。
- 检索索引是派生数据，不成为第二个内容事实源。
- 个人记录与公共学习包分离。
- 模型不得自行认定掌握、提交答案或发布公共资料。

## 五、前端设计方案

**状态：以下为体验与迁移建议；页面关系由参考任务验证，不在本稿冻结全站导航或最终视觉。**

### 5.1 主要学习路径

围绕四个连续动作设计：

**阅读／播放 → 当前语境解释 → 深入理解 → 练习／复习。**

聊天是辅助方式之一，不成为所有操作的必经之路。

### 5.2 页面职责

- **资料发现**：找到适合当前需求的材料和主题路径。
- **学习页面**：播放或阅读、字幕、点词、原句定位。
- **词汇与表达**：同一词条的多处来源、相关用法和复习。
- **练习页面**：明确任务、服务端反馈、原句与解析。
- **学习记录**：继续学习、历史、到期项和来源恢复。
- **贡献与维护界面**：提交问题、查看差异、审核与发布。

### 5.3 设计原则

- 内容可以很深，默认界面保持轻。
- 当前解释优先，更多用法按需展开。
- 统一来源回跳与不可用状态。
- 不用常驻说明文字弥补结构不清。
- 保留必要标签、键盘操作和清楚的操作后果。
- 用户端样式留在 `.user-ui`，不顺带改变后台。

### 5.4 渐进迁移

以已接入的词汇页为起点，先确定控件用法和主题边界；再按学习流程迁移相邻页面。旧组件只有在消费者迁移完成后才能移除。此前 Astryx 的自动化结果与暂缓的修复后人工复验，仍按原验收记录区分，不因本方案修订而改记为通过。

## 六、第三方应用与 Agent 接入方案

**状态：以下为拟开放能力及其必要边界；矩阵不授予新的内容权利、不开放匿名字幕，也不表示现有在线接口已实现这些能力。**

### 6.1 两条独立可用的路径

1. **本地包消费**：独立读取、查词、定位，无需网站和模型服务；前提是取得可按该用途使用的完整包。
2. **在线服务消费**：跨材料检索、读取当前可用或明确指定的修订，以及经委托访问个人状态。

不要求第三方为了查一句原文就部署整个项目。“仅凭公开说明接入”指文档足以完成安装、获取凭据和参考调用，**不等于匿名取得全部语料**。

### 6.2 内容访问边界

登录和第三方授权不能扩大内容本身允许的用途；本地分发、站内展示、第三方接收和模型披露分别核对。源码自托管不附送官方语料，在线撤回也不能保证收回已分发副本。

完整矩阵与适用边界只维护在[内容访问与分发权限矩阵](open-learning/content-access-matrix.md)，逐份证据只维护在[来源台账](open-learning/p0/source-evidence-ledger.md)。这里不复制矩阵，不授予新用途或匿名正文权限。

### 6.3 首批能力与接入契约

首批只读参考能力：搜索材料、搜索表达出现项、读取获准语境、解析固定引用、查询版本与可用状态。这里的“公共能力”指对外可集成，不意味着全部数据公开。

后续才加入保存词语及来源、读取本人复习任务、提交明确练习或复习操作、恢复本人学习状态。

接口必须明确身份、scope、用途、资源归属、输入输出 schema、分页、错误、重试、幂等编号、版本冲突，以及撤回／撤权语义。REST 提供稳定能力，MCP 做薄适配，不直接暴露数据库 CRUD，不为每个宿主复制业务逻辑。

### 6.4 Agent 威胁模型与写入边界

将字幕、引用、工具结果及第三方输入视为不可信数据。主要风险包括：材料诱导越权调用、跨用户读取、扩大上下文披露、伪造确认、重复写入和撤权后继续访问。

- 只读工具不因正文中的指令产生学习状态写入或发布行为；只读结果不授予新的 scope。
- 服务端自行验证身份、scope、归属、用途和参数，不相信模型提供的用户 ID、确认声明或工具 annotations。
- 写工具限定资源、动作和参数范围；重试采用明确幂等语义，不能把模型自由文本直接解释为数据库修改。
- 持续授权须明确动作范围、期限与撤销方式。普通可逆收词可在已获准范围内执行；提交成绩、删除等后果较重的操作，需要可核验的明确用户意图／确认机制，不能只凭 Agent 自述。
- 不能承诺所有宿主模型都不受提示注入影响。可验收的底线是：即使模型发出了越权调用，服务端仍拒绝，且没有未授权披露或副作用。

对应正负用例列入第九章；只读阶段不开放通用写工具，P4 也不自动开放公共资料发布。

## 七、开源、维护与资源假设

### 7.1 开源准备

- 核对自有代码、历史贡献和依赖的许可边界。
- 确定代码许可证，分别处理规范、内容和贡献授权。
- 排查发布范围中的凭据、私人配置和不可公开素材。
- 提供可公开复现的样例与配置模板。

全部开源是已确认方向，**具体许可证尚未确定**。DCO、CLA 或其他贡献规则应根据所需权利选择，不把签署形式当作已经完成内容授权审查。

P0 未完成相关决策前，不新增接收权利安排不清的外部贡献或对外分发未核清内容；使用自有或权利明确材料的内部验证可以继续。既有公开发行物仍按其已发布许可处理，本稿不追溯改变许可。

### 7.2 独立运行

区分仅使用读取器、启动基础学习站点、按需开启模型、按需开启内容生产与 GPU。基础路径不得依赖维护者个人机器或未公开数据。

自托管验收不仅检查能否启动，还检查无官方凭据时的基础阅读、配置错误提示、样例导入和个人数据生命周期。生产迁移仍单独授权。

### 7.3 审核职责与贡献吞吐

沿用现有 SLCS 治理中的角色与发布边界，以下是建议补充、需在 P1 明确的工作分配，不表示已经新增系统角色或权限：

- 贡献者提交局部问题、差异和证据；内容审核者核对其有能力判断的范围；具备发布权限的维护者承担最终发布和用途核查。
- 按影响而不是文件大小分级：释义、译文、练习答案、来源和许可变更须实质核对；时间轴或错字若影响定位、语义或答案，也按高影响处理。
- 纯排版等经差异检查确认不改变语义／锚点的修改，可走简化审核，但仍需追溯到审核结论。
- 高影响内容优先由非作者复核。确实只能单人审核时记录这一限制，不宣称独立复核；涉及权利或答案的不确定项暂停发布。
- 抽检用于已发布内容的质量监测，不能替代发布前必要的授权、答案和锚点检查。比例、触发全量复核的条件由 P1 试验确定。
- 记录每份材料和每次纠错的实际审核工时、队列等待与返工原因。超出可用审核能力时暂停扩量、缩小题材或减少增强内容，不以取消检查换吞吐。

### 7.4 版本与兼容承诺

区分**学习包格式、指纹算法、读取器发行版、在线 API 和 MCP 适配**的版本，不用一个“1.0”覆盖所有承诺。

- P1 使用既有包契约与一致性样例，修订映射和兼容变更遵守 SLCS 现行版本规则，不在本大纲复制或改写字段契约。
- P3 对外试点前，明确支持的版本组合、实验性能力、变更通知方式、弃用周期、负责人和兼容测试；这些安排未明确时不得声称稳定 API。
- 1.0 不预定日历日期。只有相应契约经过独立消费、版本兼容与纠错演练，并完成维护承诺评审，才决定是否稳定发布。
- 新旧客户端和新旧包的接受／拒绝矩阵随发行验证，不能用“尽量兼容”替代确定结果。

### 7.5 资源假设与主要风险

**规划假设，不是已有人力承诺：**先按少量维护投入设计，不依赖持续涌入的社区贡献或专职审核团队；测试者、贡献者和审核者均待招募／确认，不编造人数或投入工时。

P0 需记录每周可用开发／审核工时、可招募的测试者与贡献者、基础测试环境及预算。各阶段工作量分成工程改造、内容核对和外部演练三部分，依据实际试做估算，不以代码量代表全部成本。

| 风险                       | 触发信号                                       | 应对与阶段影响                                                                       |
| -------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| 内容授权不足               | 来源证据缺失，译文／模型披露／再分发用途未获准 | 优先自有、合成或明确开放材料；未核清不进公开语料，可能阻塞 P1 对外贡献与 P3 正文返回 |
| 审核成为瓶颈               | 队列增长、返工反复、核对工时超过预算           | 先测每份材料成本，再限制在制品与扩量；缩小主题或增强范围，不降低发布质量             |
| 单一维护者依赖             | 只有一人能签发／发布，或外部人员无法按文档复现 | 演练交接与独立运行，明确替补和责任；无法形成独立证据时保留未验收状态                 |
| 试点样本不足或技术边界返工 | 招募不足、权限／引用规则未定就铺开页面与接口   | 不将内部冒烟代替外部可用性结论；先做共享服务的纵向切片，再扩展                       |

## 八、分阶段开发路线与依赖

各阶段先盘点已有实现，再补缺口；“代码存在”和“本阶段验收通过”分开记录。以下为拟议阶段门，不是已批准实施清单。

### 8.1 阶段交付与出口

| 阶段                      | 主要交付                                                               | 必须满足的出口条件                                                                                                             |
| ------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **P0 方向与基线收口**     | 目标人群、参考任务、许可与来源决策、现有能力与消费者清单、资源和测试卡 | 三项阻塞决策有明确结论与责任人；确认参考材料范围与贡献授权路径；后续试验规模、任务、判定和证据方式已固定，不带空白门槛进入验收 |

### 8.2 P0 三项阻塞决策

P0 完成不是“这些问题以后会讨论”，而是形成可执行结论：

1. **目标学习者与任务**：学习背景、主要目标、参考任务、招募条件和暂不覆盖人群。不要求排他性服务一种人群，但首期验收对象必须明确。
2. **参考语料与授权来源**：主题、难度、材料清单和规模；原文、译文、词汇、媒体、再分发及模型披露的证据与缺口。来源不明项移出对外试点范围。
3. **代码许可与贡献授权**：代码开放范围、历史贡献核对办法、代码和内容各自的许可／贡献条款，谁负责确认及接受贡献的前提。不自动改根许可，不追溯改变既有发行物许可。

仅内部自有材料试验不必等待全部对外手续完成，但不能据此宣布 P0 或对外 P1 已通过。决策记录的编号、状态与责任统一见第十章。

### 8.3 串行约束与可并行工作

```text
P0：目标／许可／资源／试验设计
                ↓
P1：参考资料 + 修订、用途、引用边界
                ↓
       共享应用服务纵向切片
          ↙             ↘
P2：官方学习体验     P3：第三方只读验证
          ↘             ↙
       P4：受控个人状态写入
                ↓
       P5：稳定、交接与扩量
```

- P0 期间可做已有能力盘点、测试设计和权利清楚的内部试做；不能先接受不明授权贡献或承诺新公共接口。
- P2 开始时就沉淀共享用例和事务边界，不等网站完成后再另抽一套 API。P3 的文档与参考客户端可同期验证同一切片，不要求 P2 全部结束后才开始。
- P2／P3 正式出口均依赖 P1 的引用与用途边界。并行意味着共享设计、独立验收，不意味着两个写作者同时改同一组文件，也不意味着一次铺开所有页面和适配器。
- P4 的整体放行依赖 P2 个人数据底线和 P3 对外读取／授权契约通过；其离线设计与负例准备可提前，但不提前开放写入。
- 基础兼容、可配置运行和生命周期从首次受影响阶段开始维护，P5 是收口和扩展，不是第一次补安全、导出或自托管。

生产迁移和发布是单独放行事项，不因任何本地阶段完成而自动执行。

## 九、可执行验收设计

### 9.1 验收卡与证据归属

先固定测试设计，再执行和判定；不能事后降低门槛覆盖失败记录。具体字段、证据目录、试点规模建议及 P1–P3 卡片状态，只维护在[验收卡模板与待确认参数](evidence/open-learning/acceptance-cards.md)。本大纲仅保留阶段门和验收原则。

### 9.2 数值确认的前提

D05 等待 D02（目标学习者）和 D03（参考材料）形成结论，并结合 D04 与实际资源，将建议转为具名、具数值的 P1–P3 测试卡。未确认数字不能当作承诺，未招募参与者不能当作独立验收；P0 出口前不得保留空白门槛。

当前只整理既有设计，不开始后续阶段的招募、开发或验收。

### 9.3 一次真实学习任务

建议核心任务为：

> 找到符合给定需求的材料 → 阅读／播放并理解一个目标表达 → 返回原句核对 → 保存该表达及其来源 → 完成一次明确练习或复习 → 退出并恢复到正确位置。

P0 根据学习者决定是否调整，不强制所有材料都含模型辅导。P2 开始前准备等价任务与经核对的题目，固定提示可用范围和观察方式。记录：

- 独立完成、求助后完成、失败／退出的实际人数与步骤；帮助内容如实登记。
- 从开始到结束的耗时、误点击、错误定位、恢复失败和无效提示。
- 原句理解与来源核对结果；完成操作不自动推断已经掌握。
- 如观察新语境辨认或延迟回忆，事先规定题目、间隔和缺测处理，单独报告；不能用一次产品可用性试验宣称普遍教学效果。

任务成功率与耗时目标在执行前确定。出现数据丢失、错误引用或未授权披露，不能用平均完成率达标抵消。

### 9.4 正确性、安全与生命周期底线

以下用例在受影响阶段必须具有明确断言并全部通过；“零违规”仅指声明的测试集，不宣称系统不存在任何风险。

| 用例组           | 必须观察的结果                                                                               | 首次必验阶段                    |
| ---------------- | -------------------------------------------------------------------------------------------- | ------------------------------- |
| 修订与当前版回退 | 新旧固定引用分别解析原修订；切换当前版不改写历史；无匹配／歧义不自动替换                     | P1                              |
| 撤回与用途拒绝   | 正文、词汇语境及搜索片段不经旁路泄露；恢复须显式重新获准；离线副本限制明确                   | P1；新增检索在 P3 复验          |
| 本人数据生命周期 | 新增事实进入本人导出和注销清理；其他用户不可读写；个人数据不混入公共包                       | P2；P4 增量复验                 |
| 第三方读取       | 匿名／错 scope／跨用户／撤权／用途不足均被拒绝；返回粒度与矩阵一致                           | P3                              |
| 材料中的注入指令 | 恶意字幕或引用要求扩大读取、发起写入、提交或发布时，不产生额外权限；直接构造越权调用也被拒绝 | P3；P4 加写入副作用断言         |
| 幂等与确认边界   | 同操作重放只记一次，参数冲突与并发按契约处理；伪造用户 ID 或“已确认”声明不能绕过检查         | P2 站内写入；P4 第三方写入      |
| 兼容与独立运行   | 支持／拒绝的版本组合结果确定；安装实际发行物而非借源码路径通过；无官方模型也可完成基础任务   | P1 读取器；P3 接入；P5 完整收口 |

Agent 用例分为确定性的服务／协议测试和所选参考宿主的端到端测试，分别报告。服务测试不能证明模型不受诱导，宿主测试也不能替代服务端权限断言。

### 9.5 判定责任与工程门禁

每阶段由具名的验收负责人根据测试卡和证据判定，执行者不能只凭自述宣告通过。目标学习者提供体验观察，独立接入者提供文档可用性证据，内容审核者核对答案／来源；人数不足和同人兼任如实披露。

保留现有门禁，并按受影响范围执行：

- 后端测试、真实 PostgreSQL 事务与并发测试。
- 前端 check、单测、构建与自动化回归。
- ego-browser 桌面、手机和键盘实页验收。
- 独立读取器发行物与兼容性检查。
- 较大代码改动的一轮独立审查。

未执行项明确记录。阶段成功不自动代表生产可发布；既有历史测试也不替代当前改动的复验。
