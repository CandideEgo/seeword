## 1. 结论摘要

1. **AGPL v3 仍是自有应用代码的优先候选，但现在不能直接替换根 LICENSE。** 分域许可、依赖告知、源码提供方式和未来贡献规则尚需收口。
2. **GSAP 是可避免的依赖问题。** 初次扫描未发现运行消费者，只有遗留注释；官方条款有用途限制。“免费商用”不等于可以把它作为无额外限制的 AGPL 代码发布。随后用户明确批准移除，依赖清理及验证结果见第 7 节，未重写动画。
3. **Sharp/libvips 与 Lightning CSS 不应因含 LGPL／MPL 就被直接判定必须替换。** 应区分包装库、原生库、构建工具及实际分发物，履行各自许可与源码／告知义务。
4. **现有本地 Next standalone 产物需要补发行合规核验。** 发现包清单／原生包保留，但对应 LICENSE 文件未保留；不能只依赖 Next tracing 自动带齐告知。该观察仅来自本地 Windows 旧产物，不是生产镜像违规认定。
5. **Python 的部分“未知许可”是元数据缺失，不是无许可。** 已补取 81 个精确版本的 PyPI 元数据，并校验 13 个 wheel 中的 14 份许可文件；其中 pyannote 系列和 TorchCodec 的原始许可已定位。
6. **模型权重和 LiteLLM 可选网关仍须单独收口。** 包代码许可证不许可模型权重；LiteLLM 固定源码明确有企业许可区域，不能以 MIT 覆盖整个镜像。可选组件的未决不等于基础阅读必须推倒重做。

## 3. 逐项核对

### F01 · GSAP 3.15.0：用途受限，且当前未发现运行消费者

**核对时事实（移除前）。** [package.json](../../../frontend/package.json) 和锁文件当时保留 GSAP；对应已装包为 3.15.0，许可字段指向 [GSAP Standard No Charge License](https://gsap.com/standard-license/)。实际搜索 `frontend/src`、`scripts`、`e2e` 的相关源码／样式／HTML，只得到 6 处注释，没有发现导入或调用。具体匹配见本地证据；[PageTransition](../../../frontend/src/components/common/PageTransition.tsx) 与 EmptyState 已使用 CSS 动画。注释中仍有旧 GSAP 描述，不能当运行事实。后续移除结果见第 7 节。

**原始条款。** 官方页面标注生效日 2025-04-30、最后修改日 2025-05-30。许可限定 Permitted Uses，并限制参与构造与 Webflow 可视化动画能力竞争的工具、相关逆向和移除专有告知；FAQ 允许免费商业使用。它不是无条件的 MIT／Apache 授权。该页为本次读取的现行条款，不冒充安装当日的历史条款快照。

**结论：需调整依赖／发布范围，不能直接按 AGPL 覆盖 GSAP。** 这些额外用途限制与项目希望下游可自由修改、分发的目标存在实质张力；具体组合的法律边界未作终局认定，也不据此断言当前英语学习站使用 GSAP 违法。

**最低成本整改方向：**移除未使用的直接依赖及其锁文件条目，并做依赖、构建和受影响回归验证。无需新增动画库替代一个未使用的库。初次核对未实施；随后已取得用户授权并按第 7 节完成移除，未将 GSAP 改头为 AGPL。

### F02 · Sharp 0.35.5／libvips：有条件保留，先核验实际发行物

**事实。** Next 16.4.3 声明 Sharp，项目没有发现直接使用 Sharp 的源码；[Next 配置](../../../frontend/next.config.js) 的 `images.unoptimized=true` 只说明图片不走优化器，不证明 Sharp 从发行物中消失。[Dockerfile.prod](../../../frontend/Dockerfile.prod) 复制 standalone、静态资源与 public，目标为 Alpine Linux。

- 已装 Sharp 主包许可为 Apache-2.0，已读取原文。
- 当前 Windows 原生包 `@img/sharp-win32-x64@0.35.5` 声明 Apache-2.0 AND LGPL-3.0-or-later，包含 libvips DLL；其 versions.json 记录 vips 8.18.7 及多项底层库。
- 精确上游 [libvips v8.18.7/LICENSE](https://raw.githubusercontent.com/libvips/libvips/v8.18.7/LICENSE) 是 LGPL 2.1 文本。不能用主库这一份文本覆盖 Windows 组合二进制的全部组件／许可，也不能把两个声明当作同一个包装层。
- [Sharp 安装说明](https://sharp.pixelplumbing.com/install/) 明确按平台选择预构建二进制；Windows 的许可与链接证据不能替代 Alpine Linux 的实际包。

**结论：不是必须替换；需补告知、相应源码与链接／替换条件的发行核验。** Apache 部分保留许可、版权及适用 NOTICE；LGPL 部分按实际组合版本核对通知、源码获取和用户修改／替换库的条件。选择合适的共享库机制可以是履行路径之一，但必须验证，不能仅凭有 DLL 就宣告全部条件满足。

**已发现的产物缺口。** 现存本地 Windows standalone 中有 Sharp 与原生包的 manifest，但没有各自 LICENSE；按 LICENSE／LICENCE／NOTICE／COPYING 命名前缀扫描整个 standalone，未找到独立告知文件。这不是扫描所有 bundle 内嵌告知的结果，也不能直接判定历史生产违规；但足以否定“standalone 自动保证带齐第三方许可”的假设。

**待满足条件：**针对实际 Linux 发行物列出进入包／镜像的组件与版本，保留许可和 NOTICE，给出必要源码及替换／重链接说明；确认产物、告知清单与源码入口相互对应。本轮未构建镜像或整改。

### F03 · Lightning CSS 1.32.0／1.33.0：保留 MPL，不把构建工具整体改成 AGPL

**事实。** 1.32.0 由 `@tailwindcss/node@4.3.2` 引入，项目 [PostCSS 配置](../../../frontend/postcss.config.js) 采用 Tailwind 插件；1.33.0 位于 Vite 的嵌套依赖中。两处已装 LICENSE 与各自上游标签原文的 SHA-256 一致：

- [v1.32.0/LICENSE](https://raw.githubusercontent.com/parcel-bundler/lightningcss/v1.32.0/LICENSE)
- [v1.33.0/LICENSE](https://raw.githubusercontent.com/parcel-bundler/lightningcss/v1.33.0/LICENSE)

**条款。** MPL 2.0 第 3.1–3.4 节规定受覆盖文件的源码、可执行形式及告知义务，并允许符合条件的 Larger Work；第 1.12／3.3 节涉及 Secondary Licenses，但不能仅凭许可模板中有 Exhibit B 就推断项目实际附加了不兼容声明。

**结论：有条件保留。** 本项目没有必要把独立构建工具本身改发为 AGPL。分发包含该工具的开发／构建镜像或二进制时，需保留 MPL 通知，并提供对应受覆盖文件的源码获取办法；若修改了受覆盖文件，按 MPL 处理。不能仅因生成了 CSS 就推定所有生成结果都受 MPL 约束，也不能把“仅构建时使用”当作分发构建镜像时完全无义务。

目前只确认了许可文本一致，未对包内全部代码逐文件证明“未修改”，也未完成实际发布物的 MPL 源码清单。

### F06 · 模型权重、FFmpeg 与数据：本轮不能放行

- [GPU 配置](../../../gpu-worker/gpu_worker/config.py) 允许模型名／路径和对齐模型覆盖；[模型加载器](../../../gpu-worker/gpu_worker/transcription/whisper_model.py) 可能按语言自动选取对齐模型。
- WhisperX 3.8.6 的代码默认英语对齐入口指向 `WAV2VEC2_ASR_BASE_960H`；标点包默认模型名为 `oliverguhr/fullstop-punctuation-multilang-large`。它们说明可能的选择入口，不证明 GPU 主机实际下载的权重、revision 或许可条件。

- ECDICT、字幕、媒体和模型各自的权利边界仍与自有应用代码分开。本轮未下载模型、读取 GPU 配置凭据或业务数据。

**结论：待进一步确认；对相应权重／二进制／数据的打包分发保持阻塞。** 最少需要实际模型标识与 revision／哈希、模型卡及许可、发行包清单与 FFmpeg 构建信息。基础阅读不应因此强制附带这些资产。

### F07 · LiteLLM 可选网关：根 MIT 不覆盖企业目录

项目 [image-lock.json](../../../deploy/v2-gateway/image-lock.json) 固定源码提交 `61c6ab78393ef45683dd7d963d2a315bd845e20b` 和镜像摘要。实际核对：

- [固定提交根 LICENSE](https://raw.githubusercontent.com/BerriAI/litellm/61c6ab78393ef45683dd7d963d2a315bd845e20b/LICENSE) 明确排除 `enterprise/`，其他适用部分为 MIT。
- 企业条款实际文件为 [enterprise/LICENSE.md](https://raw.githubusercontent.com/BerriAI/litellm/61c6ab78393ef45683dd7d963d2a315bd845e20b/enterprise/LICENSE.md)，不是本地记录中所写的无扩展名路径。它要求生产使用满足企业协议／有效许可，并对分发等权利作限制；不是 MIT 或 AGPL。
- 生产 Compose 将这些服务放在 **`llm-gateway` 可选 profile**，不是基础阅读站点的强制依赖。薄适配器与上游网关通过 HTTP 交互，不能仅凭连接就将上游企业代码重新许可为 AGPL。

**结论：普通 MIT 部分与企业部分分别处理；该可选网关的发行边界未放行。** 本轮没有拉取或检查镜像层，不能断言实际镜像包含／执行哪些企业代码，也不据此断言现有部署违法。放行前需证明使用与分发范围只涉及获准部分，或具有相应权利；整个上游镜像不能笼统写成全 MIT。

查证过程曾取得两个 404 页面：企业文件应为 `LICENSE.md`，libvips 文件应为 `LICENSE` 而非 `COPYING`。即使提取工具返回空 failed 列表，错误页也未算通过；通过固定版本目录 API 找到正确路径后才取得原文。未为图方便改读 main 或其他版本。

## 4. 适用范围与贡献授权建议

以下是基于本轮证据的建议，**不是用户已批准的许可决定或已实施规则**：

- 自有应用代码继续以 AGPL v3 为优先候选；最终文件范围、版本标识、源码入口及告知交付方案需同时确认，不给第三方库统一改头为 AGPL。
- 独立 SLCS 已有 Apache／CC 分域许可继续有效，不因根应用选型自动重许可；内容与用户数据同样不能由根软件许可包办。
- 第三方应用仅接入 API，不仅因调用协议就被推定必须全项目改用 AGPL；真正的代码复制、链接或衍生组合仍按具体边界判断。
- 对未来自有代码贡献，优先考虑 **inbound=outbound + DCO 1.1**，即按项目适用许可提交，并确认有权提交；本轮已核对 [DCO 官方原文](https://developercertificate.org/)。DCO 不是版权转让、额外再许可授权，也不是 AI 共同署名。
- 暂无依据为当前目标引入版权集中转让或复杂 CLA。若将来确需双重许可等权利，再另行评估，不能从这次全部开源决定推定。
- 历史用户署名确认不代替第三方来源声明；不追溯伪造签署记录。DCO 机制、公开个人署名信息的影响和内容贡献规则仍需明确批准；未新增贡献入口、CI 门禁或自动补签。
